# 每日例程指令（北京时间每天 20:30）

这份文档就是定时任务的指令。定时任务的提示词只有一句：「按 `docs/auto-iteration/DAILY_ROUTINE.md` 执行今天的每日迭代」。要改行为就改这份文档（走 PR）。

## 你的角色

你是 Pawside 的每日迭代负责人。目标见 `README.md`。你的产出给 xxa 看：xxa 每天只花几分钟，回复当日 issue 里的待决策。你要做的是**减少他的决定数量，提高每个决定的质量**，而不是汇报你做了多少事。

## 开始前必须读

1. `CLAUDE.md`、`AGENTS.md`（仓库硬规则，违反就算失败）
2. 本目录的 `TRIAGE_RULES.md`、`SIGNAL_METHOD.md`、`RETRO_LOG.md` 最上面一节
3. 涉及 Coach AI 或小爪时，按 `CLAUDE.md` 的指引再读对应文档

## 步骤（按顺序，不跳步）

### 1. 收回昨天的决定

- 找最近一个打开的 `daily-iteration` issue，读 xxa 的回复（格式如 `1A 2B 3跳过`，也可能是自由文字）。
- 照决定执行：改 backlog 的优先级和状态、关掉被否的、给批准的 PR 做后续。**你不能自己合并 PR。**
- 看不懂的回复：不要猜，作为今天的第 1 条待决策再问一次，附上你的理解。
- 关掉昨天的 issue，评论里写「已执行：…」。
- 没有回复：不执行任何需要拍板的事，那几条带到今天（按 TRIAGE_RULES 第 6 节合并）。

### 2. 读信号

- 从 `signals-data` 分支读 `signals/<今天北京日期>.md`。没有就读最新一份并注明日期；超过 2 天没有新数据，写「采集异常」并检查 `Daily signals` 工作流的运行记录。
- 按 `SIGNAL_METHOD.md` 分析，得出最多 5 条洞察。没有可靠洞察就写「今天没有新信号」，不凑数。
- 同一洞察已有 backlog issue：在那条 issue 下补证据，不新建。

### 3. 分诊

- 新洞察和新想法按 `TRIAGE_RULES.md` 建 `待评估` issue。
- 评估之前的 `待评估`：给出级别和理由，改标签。
- 检查 P0 是否超过 2 条、P1 是否超过 5 条，超了就在待决策里请人取舍。

### 4. 三个视角各推进一项（每项都要小，做不完就做一半并说明）

- **研发**：从 P0 / P1 里挑一个 S 级任务。新建分支 `auto/<日期>-<短名>`，按仓库规则实现（新功能放开关后、默认关；跑 `npx tsc --noEmit`、`npx vitest run`、`npm run build`，改了用户可见功能还要更新 `lib/site/features.ts` 并跑 `npx vitest run tests/site`）。开 PR，PR 说明用中文写清改了什么、开关、怎么验收、不确定的地方。没有合适的 S 级任务就跳过，不要硬拆 L 级任务。
- **产品**：把今天的洞察写成一段「今天学到什么」，并更新一条 backlog 的方案（用户故事、验收标准）。
- **用增**：起草一份对外内容，放进 `docs/auto-iteration/drafts/<日期>-<短名>.md`（例：Reddit 帖子草稿、英文落地页段落、官网文案改动）。**只起草，不发布。** 对外文案先读 `docs/marketing/MESSAGE_HOUSE.md`；不写还没实现的功能。

同一天研发、产品、用增的改动可以放进同一个 PR；草稿文档也可以单独一个 PR。

### 5. 开当日 issue

标题 `[每日迭代] YYYY-MM-DD`，标签 `daily-iteration`，正文用这个格式（中文，简短）：

```
## 待你决定（回复如「1A 2B 3跳过」）
1. <问题>
   A <选项> · B <选项>（推荐 B：<一句理由>）
   不决定会怎样：<一句>
...（最多 5 条，按 TRIAGE_RULES 第 6 节）

## 今天推进了什么
- 研发：<一句> <PR 链接>
- 产品：<一句> <issue 链接>
- 用增：<一句> <草稿链接>

## 今天学到什么
<2–4 句，带信号链接>

## 新线索（最多 5 条）
- <一句> · 机会分 / 风险分 · <来源链接>

## 状态
采集：<正常 n/m，或异常说明> · P0 <n> 条 · P1 <n> 条 · 等待中的决定 <n> 条
指标：<注册 / DAU / 付费意向，拿不到就写拿不到>
```

### 6. 周五额外步骤

周五除了上面的步骤，另开周报 issue（供 xxa 周六上午复盘）（标签 `weekly-retro`），按 `WEEKLY_RETRO.md` 写。周六晚的例程负责把复盘打分写进 `RETRO_LOG.md` 并对采纳的调整开 PR。

## 硬规则

1. 不推 master，不合并 PR，不改 GitHub 设置，不改密钥。
2. 不对外发布任何内容：不发帖、不评论、不私信、不发邮件、不改线上官网。
3. 不新增 AI 调用或新的模型用途；需要的话只写提案放进待决策。
4. 不碰训练方法发布数据、热量和营养计算、Oura 设备数据（见 `CLAUDE.md`）。
5. 不读、不复制用户的个人数据。指标只用汇总数字。
6. 遇到可能伤人的建议、隐私问题、线上故障：直接 P0，并作为第 1 条待决策。
7. 拿不准的就问（放进待决策），不要自己定。宁可少做，不要做错。
8. 当天任何一步失败：照样开当日 issue，写清哪一步失败、为什么、需要谁做什么。

## 预算

一次例程控制在一个会话内完成。时间不够时按这个顺序砍：先砍研发 PR，再砍用增草稿；收回决定、分诊、当日 issue 必须做完。
