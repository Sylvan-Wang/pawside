# 例程指令（北京时间：周日到周四 9:30，周五、周六 20:30）

开始前先读 [COLLABORATION.md](COLLABORATION.md)（合作规范和授权）和 [P0.md](P0.md)（P0 永远排第一）。两个定时任务共用这份指令：早 9:30 的「执行场」（周日锁定、周一到周四执行）不推需要 xxa 决策的事项；晚 8:30 的「决策场」（周五规划、周六跟进）集中放所有需要人工决策的事。

定时任务的提示词只有一句：「按 `docs/auto-iteration/DAILY_ROUTINE.md` 执行今天的例程」。要改行为就改这份文档（走 PR）。

## 节奏（2026-11-07 与 xxa 确定）

xxa 工作日没法上线，周末集中处理。所以：

| 哪天 | 模式 | 给 xxa 的产出 |
|---|---|---|
| 周一到周四 | **执行** | 只在当周计划 issue 下追加一条简短进展评论。不开新 issue，不提新问题 |
| 周五 | **执行 + 规划** | 先做当天任务，再开周计划 issue：本周复盘 + 下周任务清单 + 待批事项 + 需要 xxa 动手的事。xxa 周六一早就能看到 |
| 周六 | **跟进** | 处理 xxa 周六的批复（较轻，约半小时）；把仍需讨论的、需要动手的重活整理到周日 |
| 周日 | **锁定** | 处理 xxa 周日的批复和动手结果（较重），定稿下周计划，记复盘日志 |

例外只有一种：P0 紧急事件（线上故障、安全、隐私、可能伤人的建议）可以在工作日单独开 issue，标签 `P0`，并 @caizhenyu-nb。其他一律等周五的周计划。

**启动规则**：如果没有打开的 `weekly-plan` issue（例如第一次运行），不管今天周几，先按规划模式出一份周计划。

## 不灌水规则（所有模式都适用）

1. 每一条进展都必须附可查的产物：PR、commit、issue、草稿文件的链接。没有产物的不写。
2. 不写「调研了」「梳理了」「在推进」「规划中」这类没有产物的动词。
3. 没有进展就写一行「今天无进展：<原因>」，不凑内容。
4. 任务必须小到一天内能做完，并带可验证的验收标准。说不清怎么验收的任务不进计划。
5. 不报数量（「处理了 12 条信号」），只报结果（「新增 backlog #45，证据 3 条」）。
6. 拿不准的事写进下一次周计划的待批事项，工作日不问。

## 执行模式（周一到周四早 9:30；周五晚先做当天任务）

0. **先看小爪健康度。** 读当天 `Coach eval` 工作流（GitHub Actions，北京 9:00 自动跑）的结果；能连上数据库时再查线上 `ai_generations` 近 24 小时的失败率和失败原因（连不上就在当日 issue 里注明没查）。评测掉分或线上失败率超过 5%：这是 P0，当天先开修复 PR（改提示词要升 `PLAN_PROMPT_VERSION`），再做别的。

1. **采集信号，不打扰人。** 读 `signals-data` 分支 `signals/<今天北京日期>.md`，按 `SIGNAL_METHOD.md` 分析。新洞察按 `TRIAGE_RULES.md` 建 `待评估` issue 或给已有 issue 补证据。采集异常只记下来，周五一起报。
2. **只做已锁定计划里的任务。** 按计划顺序取今天的任务，做不完就留到明天，不换题、不加题。
   - 研发任务：分支 `auto/<日期>-<短名>`，按仓库规则实现（新功能放开关后、默认关；跑 `npx tsc --noEmit`、`npx vitest run`、`npm run build`；改了用户可见功能要更新 `lib/site/features.ts` 并跑 `npx vitest run tests/site`）。开 PR，中文说明改了什么、开关、怎么验收、不确定的地方。不合并。
   - 产品任务：产出写进 issue 或 `docs/` 下的文档。
   - 用增任务：草稿放 `docs/auto-iteration/drafts/<日期>-<短名>.md`。只起草，不发布；对外文案先读 `docs/marketing/MESSAGE_HOUSE.md`，不写还没实现的功能。
3. **在周计划 issue 下追加一条评论**，格式固定：

```
<日期> 进展
- ✅ <任务名>：<一句结果> <链接>
- ⏸ <任务名>：卡在 <什么>，周末处理
（没有进展：今天无进展：<原因>）
```

## 每周安全巡检（周五，规划之前做；结果写进周计划「本周复盘」）

目标：别人拿不到也用不了我们的 OpenAI 密钥，也没法靠刷接口烧钱。逐条检查，有问题当天修（走 PR），发现泄露或异常消耗按 P0 处理。

1. **跑自动检查：** `npx vitest run tests/security`。它会拦住两类问题：密钥变量出现在浏览器端（`NEXT_PUBLIC_*`）；AI 接口没有登录检查或没有限流。
2. **查密钥有没有进仓库：** 在最近一周的提交里搜 `sk-`、`OPENAI_API_KEY=`、`service_role`。搜到了就是 P0，立刻告诉 xxa 去 OpenAI 后台作废并换新密钥（只有 xxa 能操作）。
3. **查新增的 AI 入口：** 本周新增或改动的 `app/api/**/route.ts`，凡是会调用模型的，都要先检查登录，并且有按用户的限流。
4. **查用量：** 读 `Coach eval` 和线上报错日志，看有没有异常调用量。例程拿不到数据库的话，在周计划里写「需在对话里查 `ai_generations` 近 7 天按用户计数」，由带数据库权限的会话补查。
5. **查依赖：** `npm audit --omit=dev`，high 和 critical 级别的漏洞列进下周任务。

## 规划模式（周五，做完当天任务之后）

开一个 issue，标题 `[周计划] <下周一日期> – <下周五日期>`，标签 `weekly-plan`。关闭上一周的计划 issue。正文：

```
## 1. 待你批（回复如「1A 2B 3跳过」）
按 TRIAGE_RULES 第 6 节选，最多 10 条。每条：问题 · 选项 · 推荐和理由 · 不决定会怎样。
本周积压的 PR 合并决定也放这里，每个 PR 一句话说清改了什么、怎么验收。

## 2. 需要你动手的事
标明「周六（轻，≤30 分钟）」或「周日（重）」。
例：填密钥、在某平台注册账号、真机测试某功能、发一条帖子。每条写清步骤和预计时间。

## 3. 下周任务清单（批完后锁定）
| 天 | 视角 | 任务 | 验收标准 | 依赖哪条批复 |
每天 1–3 条，S 级。总量按本周实际完成量估，不要超过本周完成量的 1.5 倍。

## 4. 本周复盘
- 计划了几条、完成几条（列链接）、没完成的原因
- 本周最有价值的 3 条信号，以及它们后来怎样了
- 采集健康：哪些来源一直失败
- 指标：注册 / DAU / 付费意向（拿不到就写拿不到和原因）
- 建议的系统调整（最多 3 条，写成可选项，放进第 1 节）

## 5. 请你打分
线索质量 1–5 · 待批事项质量 1–5 · 推进速度 1–5 · 哪里浪费了我时间
```

## 跟进模式（周六）

1. 读 xxa 周六在周计划 issue 里的回复，照批复执行可逆的部分（改 backlog、开草稿 PR）。
2. 在 issue 里评论：已处理哪几条；还剩哪几条留到周日，每条一句话说明为什么需要周日处理。
3. 不新增待批事项，除非周六的批复引出了新问题。

## 锁定模式（周日早 9:30）

1. 读 xxa 周六、周日在周计划 issue 里的全部回复，照批复执行：改 backlog 优先级和状态、关掉被否的。**你不能自己合并 PR**，xxa 批准合并的 PR 由 xxa 合并或明确授权。
2. 按批复修改第 3 节任务清单，在 issue 末尾评论「已锁定」并贴出最终清单。没回复的待批事项不执行，相关任务从清单里拿掉。
3. 把打分和意见追加到 `RETRO_LOG.md`，对被采纳的系统调整开 PR。
4. 看不懂的回复：不要猜，在评论里写出你的理解并标「按此理解执行，如有误请周内回复」，只用于可逆的事。

## 硬规则

1. 不推 master，不合并 PR，不改 GitHub 设置，不改密钥。
2. 不对外发布任何内容：不发帖、不评论外部网站、不私信、不发邮件、不改线上官网。
3. 不新增 AI 调用或新的模型用途；需要的话只写进待批事项。
4. 不碰训练方法发布数据、热量和营养计算、Oura 设备数据（见 `CLAUDE.md`）。
5. 不读、不复制用户的个人数据。指标只用汇总数字。
6. 当天任何一步失败：在周计划 issue 评论里写清哪一步失败、为什么、需要谁做什么。

## 预算

一次例程控制在一个会话内完成。时间不够时，执行模式先砍研发任务、保住进展评论；规划模式必须把第 1、3 节写完。
