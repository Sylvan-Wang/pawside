## 第一部分：决策日志

### A. 范围与架构

**D-01 本轮做"文字闭环"，不做照片、语音、食谱、偏好、站内气泡。**
- 做了：文字记饮食（含粗记录）、对话纠正、已保存餐的修改、实际运动补记、体重、查询某天情况、取消、一次追问预算、日期与时区、幂等与冲突、开关、导出/删除登记、隐私文案。
- 没做，原因见 `XIAOZHUA_PATCH_ASSESSMENT.md` §3-C：照片（Storage 桶是线上基础设施、视觉模型能力未验证、需要 30 例标注集）、语音（需真机和转写服务验证）、食谱（**没有指定 UP 主链接**，Patch 明确不得用虚构链接通过）、偏好与气泡（依赖食谱和偏好表设计）。
- 这不是削减：Patch §0 说"不得由困难程度擅自削减"，所以这些作为**带阻塞原因的待办**列在这里和第二部分，而不是悄悄不做。发布闸门（Patch §12）因此**不成立**，不能对外说"整版完成"。
- 备选：把照片/语音按"写了但没验证"的方式也做出来。放弃原因：Patch §11 明确"mock 不能替代真实模型/实机"，写出来却无法验证，只会制造"看起来完成"的错觉。
- 可逆：是（纯增量）。

**D-02 一次结构化"计划"+ 服务端执行；不做原生工具调用、多 Agent、流式。**
- 依据：Patch §4（"一个助手＋确定性工具调度即可"）、你要"最快的模型"、写入必须可靠。每轮最多 1 次计划调用 + 1 次批量食物估算。
- 详见 `XIAOZHUA_PROMPT_GUIDE.md` §1。
- 可逆：是。要开放式对话时再引入原生工具调用，现有工具/槽位定义可直接映射。

**D-03 聊天只能生成"草稿"，写入只能经确认接口，且确认只提交服务端保存的内容。**
- 依据：Patch §1（所有日志新增/修改都要明确确认）、§4（模型不能直接写）。
- 实现：`coach_drafts` 表；`payload`/`request_id`/`kind` 被触发器冻结；状态只能沿允许的边移动（契约测试 `coach_chat_contract.sql` 验证，并做过"关掉触发器应当失败"的变异检查）。浏览器只发"确认哪张卡、哪个版本"。
- 效果：模型被注入、读错、胡说，最坏结果是**多一张用户能看出来的卡片**，不会改记录。

**D-04 文字里说"确认/好的保存"不会保存，只提示去点卡片上的按钮。**
- 依据：Patch 写的是"点击确认或清晰的『确认保存这张卡』"，我取更保守的一半。文字确认让"模型读懂了确认"成为写入路径上的一环，这正是 D-03 想避免的。
- 代价：多点一下。
- 可逆：容易（加一个确认意图 + 单张草稿 + 短句限制）。**见问题 Q9。**

### B. 数据与写入

**D-05 饮食保存用新 RPC v2（允许"只记吃了什么"）；旧页面继续用 v1；仅当编辑里含"只记名字"条目时旧编辑页才走 v2。**
- 依据：v1 要求每个条目重量>0（RPC 里写死），所以"营养待补"无法用 v1 表达；库表本身（重量与营养列可空、日汇总有 complete/incomplete/unknown）已经支持，只缺 RPC。
- 取舍：v2 是 v1 的超集，理论上可以全部切到 v2，但明早你要测试手动饮食流程，我不想让它承担新代码的风险。两套并存的成本是少量重复 SQL。
- 可逆：以后确认稳定后把旧页面也切到 v2，然后下线 v1。

**D-06 "只记吃了什么"的表示：条目重量 NULL、四项营养 NULL；不新增列，不改日汇总。**
- 依据：Patch §6.2 优先复用现有实体；"未知不是 0"在库里已经有承载（`*_data_status`）。
- 后果：只要有一个条目营养未知，该日的热量合计就是 NULL（既有语义），所以聊天读"今天"时从条目自己推导"已知合计 + 待补数量"，**并在有未知条目时拒绝给出"还剩多少"**。
- 已验证：旧的历史页、编辑页、周报页（读 `/api/weekly-log`，聚合器保持 null、不当 0）都能容忍 null；发现并修了两处不容忍的（历史页显示成"宫保鸡丁 g"；编辑页保存会悄悄丢掉没重量的条目）。
- 没改但要知道：旧路由 `/api/weekly` 把 null 热量当 0 求平均。我 grep 了全仓库，**没有任何页面调用它**，所以不影响现有界面；见问题 Q21。

**D-07 自由运动：新增幂等 RPC 和可空热量列；`POST /api/workout` 可带 request_id；运动页面的"浏览器直接 insert"本轮不动。**
- 依据：Patch §6.2 要求"尽量收敛"。收敛页面需要改运动页的保存流程（含有氧、动作明细），面大且与验收无关，我不想在你明早测试前动它。
- 后果：手动运动页仍无幂等（双击会重复）；聊天路径有。**见问题 Q12。**
- 热量：`workout_logs.calories_burned_kcal` 可空，**只存用户说的，永不估算**。

**D-08 体重：聊天写入前读当天已有行，合并后再调用既有 RPC。**
- 依据：这是我对照代码发现的真实风险（Patch 没预见到）：`save_body_metric_with_target_v1` 同一天冲突时**整行覆盖**（腰围、体脂、备注都会被写成空）。聊天只说"体重 72"，直接调用会清掉当天已有的其他指标。
- 实现：`lib/body-metrics-service.ts`（从路由原样抽出，路由行为不变）+ `mergeWeightIntoExisting`；集成测试验证腰围和备注保留。
- 单位：用户没说就用资料里的单位，并在卡片上写明；体重 20–400 kg 之外直接拒绝。

**D-09 食物匹配只接受"精确"命中；其余走估算。**
- 依据：**用本地灌入的真实种子数据实测**（`foods_clean.csv` 约 1700 个条目，原料成分表风格）：`牛奶`、`鸡胸肉`、全部菜名、`奶茶` 命中 0；`鱼` 命中 140 条；`鸡肉` 只命中 `鸡肉松`。"包含"匹配会悄悄记错食物。
- 规则：名称相等、别名相等、或去掉括号限定词后相等（`米饭(蒸,籼米)` → `米饭`）；多个精确命中时优先个人确认过的，其次有份量模板的。
- 后果：大多数真实说法（菜名、饮料）都会走估算，所以估算的质量和标注就是体验的关键。

**D-10 AI 估算不写入个人食物记忆，也不进候选表。**
- 依据：Patch §7.1："用户确认估算只表示接受本次记录，不能升级为测量真值或标准库"。现有食物页的做法是用户逐条"确认营养"后写入 `user_food_memory`（下次显示为"上次确认"，且不标估算）；聊天里用户确认的是整张卡，不是逐项营养，所以不能套用。
- 实现：估算的每 100g 数值存在草稿里（服务端生成）；保存时 `deriveItemForPersistence` 用它计算，条目标 `is_estimated=true`、依据记录为 `ai_estimate`。该字段**不在浏览器契约里**（zod 会剥掉），浏览器无法伪造。
- 集成测试验证：保存后 `user_food_memory` 和候选表都没有新行。

**D-11 份量来源优先级：用户给的克数/可换算单位 > 份量模板 > 模型估计 > 未知。**
- 依据：Patch §7.1 的顺序（去掉了照片相关项）。模型估计的重量保存时标"估算"；没有任何依据的就不存重量。
- 现实：份量模板种子只有 **15 行、覆盖 12 种食物**，所以大多数"一碗/一个"走模型估计。

**D-12 估算失败/没份量 → 保存为"只记吃了什么，营养待补"，不阻塞记录。**
- 依据：Patch §3.2 "完全算不出也可确认'仅记录吃了什么'"。

### C. 日期、追问、定位

**D-13 模型只说"哪一天"（今天/昨天/前天/具体日期），日期由服务端用用户时区算；时区必须由客户端给，无效就拒绝，不退回 UTC。**
- 回填上限 180 天（更早的请用页面补记）；未来日期拒绝。
- 凌晨（<5 点）说"晚饭/夜宵"且没说日期：问一次"昨天还是今天"。
- **见问题 Q7/Q8（规则是否符合你的习惯）。**

**D-14 没说餐别：今天的记录按时钟推测，并在卡片上写明"按时间推测，不对请告诉我"；非今天且没说餐别：问一次。**
- 时钟规则：4–10 早餐、10–14 午餐、14–17 加餐、17–22 晚餐、其余加餐。

**D-15 每个记录任务最多一次追问，由数据库约束和服务端预算保证，不靠提示词。**
- 服务端发起的问题（日期/餐别/改哪一餐）用可点选项回答，直接补全已理解的任务，不再调模型。
- 预算用完后：不继续盘问；已有的待回答问题保留为"待补"，不捏造归属（对应 F31）。

**D-16 修改对象的定位顺序：被点名的草稿 → 唯一一张待确认的饮食卡 → 对话里最近保存的那餐（24 小时内）→ 当天唯一一餐 → 问。**
- 依据：Patch §5 "不能只按『最后一条』盲选"。卡片上永远写"原来：…"，用户在确认前能看到改的是哪一餐。
- 同一餐位有多条记录：问一次，选项里带食物名。

### D. 可靠性

**D-17 提交是一个小状态机：proposed → committing → saved，每步都是条件更新。**
- 一个 request_id 对应一张草稿；内容变化 = 新草稿 + 新 request_id（旧的作废）。
- 写入结果不明（断网、超时）时：**当场用 request_id 去查回执**——查到就当作已保存；明确没写入就把卡片放回"待确认"并提示重试；连查都查不了才标"结果未知"，再点一次会先核对，**绝不换 id 重写**。
- 已保存的餐的修改用 `expected_updated_at` 做版本检查；"被打断但其实已经写进去"的修改靠"记录现在是否等于草稿内容"识别，避免把自己的成功当成冲突。
- 全部由集成测试验证，包括丢响应、断网、并发点三次、两个标签页。

**D-18 提案 24 小时过期；过期的卡不能确认。**

**D-19 同一条消息重复发送：返回第一次的回答；第一次还在处理时等它（最多 10 秒），不会再跑一遍。**

### E. 观测、隐私、开关

**D-20 `ai_generations` 只记结构（任务类型、工具调用数、状态、耗时、token），不记用户原话；失败原因映射到现有枚举。**
- 依据：Patch §9。`ai_generations.fail_reason` 是封闭枚举，新增会要改约束，所以映射到 `timeout/upstream_error/invalid_response/not_configured/rate_limited`。
- 日志里只打错误种类和数据库代码，不打错误消息（约束违反的消息会带整行用户内容）。

**D-21 对话原文保存在 `coach_messages`（用户可一键清空，随账号删除/导出）；每天最多 300 条用户消息。**
- 清空只删消息和卡片，**不删已保存的饮食/运动/体重**（它们是普通记录）。**见问题 Q6。**

**D-22 开关三层：环境变量总开关（`PAWSIDE_COACH_CHAT=0`）、按用户的 `coach_chat` 功能位、三个子功能开关（饮食/运动/体重）。默认对所有人关闭。**
- 关闭后：界面不渲染；所有接口仍各自校验（隐藏按钮不是权限控制）；数据保留。

**D-23 官网 `lib/site/features.ts` 的 `companion` 保持"规划中"。**
- 依据：CLAUDE.md 规定"内测中只用于内测用户今天就能用到的功能"。这个功能默认对所有人关闭、还没有任何用户被开通，所以现在写"内测中"不属实。你开通内测用户之后再改（`tests/site` 会拦住不该出现的说法）。

**D-24 隐私页和法律简报如实加入"小爪对话"（目前只对部分内测用户开放）。**
- 照片、语音没做，所以"不收集照片"保持不变。

**D-25 关闭面板后，如果这次保存过东西，会刷新一次页面。**
- 原因：首页等页面在打开时自己取数，之后不会知道聊天里记了东西，会一直显示旧的一天。刷新是最简单可靠的办法。**权宜之计，见问题 Q10。**

### F. 工程

**D-26 聊天的模型用独立环境变量 `OPENAI_CHAT_MODEL`（没设置就退回 `OPENAI_MODEL`），代码里不写死任何型号。**
- 依据：你要最快的模型，但我无法核实当前有哪些型号和是否支持严格结构化输出；独立变量让聊天换模型不影响日报等现有功能。

**D-27 搭了本地仿真验证环境，并把它作为测试基础设施提交。**
- 内容：Postgres 16 + PostgREST（真实的 RLS）+ 极简的登录与 OpenAI 假接口；集成测试 `PAWSIDE_IT=1` 才运行，默认 `npm test` 不受影响。
- 它让我真跑了迁移、SQL 契约、服务层、路由、浏览器。**它不是 Supabase**：没有 Auth/Storage/Realtime。
- 这个环境直接发现了两个真实问题：D-28 和下面的 D-29。

**D-28 发现：PostgREST 遇到 SQLSTATE `40001` 会一直重试，请求永远不返回。**
- 现有的 `replace_food_log_canonical_v1`（手动饮食编辑冲突）用的就是 40001。在本地 PostgREST 12.2.3 上，"两个页面同时改同一餐"会让第二个保存卡死。
- 处理：v2 用 `PT409`（返回 409）；对 v1 另写**独立迁移** `20261023000200`，只改这一个错误码，函数其余不变。**是否应用到线上由你定，见问题 Q2。线上 PostgREST 版本我看不到。**

**D-29 发现：聊天历史在"追问被回答后"刷新会整页读取失败。**
- 原因：已回答的追问草稿保留"问题"形态的内容，卡片渲染按状态而不是按内容判断，把它当运动卡读取字段导致异常。路由级测试只有 2 条消息没暴露，浏览器端到端暴露了。
- 已修，并加了回归测试。同时补了：一轮里被替换/取消的旧卡片会同步更新（否则界面上会留着过期的"确认保存"按钮）。

**D-30 历史页的餐别显示成英文 `lunch/dinner`（原有问题，手动记录也一样）：顺手加了中文映射。**

### G. 食谱（2026-10-23 追加）

**D-31 食谱是「指针库」，由服务端挑选，模型不参与。** 依据：二手 AI 整理的数据不可信，模型一旦经手就可能编出链接或热量。表默认 draft，只有已核验并发布的行才对用户可见（行级权限 + 数据库约束）。
**D-32 热量只作「视频标称」展示，不参与计算，不进用户的饮食。** 整天热量、口径不明的数字不显示；蛋白质等不填。
**D-33 有话题就只推荐匹配的，没有匹配就不推荐。** 宁可不推，也不拿无关食谱凑数。
**D-34 过滤和排序在代码里做，不把用户的话放进数据库过滤表达式。**

## 第二部分：待你回答的问题

优先级：🔴 明早测试前需要 · 🟡 本周内 · ⚪ 可以之后。每题给了"我现在假设的默认"，你说"按默认"就行。

### 🔴 明早测试前

**Q1 Netlify 函数超时是多少？**（你上一轮问过"超时是啥"）
Netlify 后台 → Site configuration → Functions 看 Timeout。聊天一轮最多 2 次模型调用（计划 + 估算），每次我设了 15 秒上限，最坏情况会超过 10 秒。如果平台上限只有 10 秒，需要把估算改成可选/拆请求。**默认：先按现状测，看 p95。**

**Q2 要不要把 `20261023000200`（手动编辑冲突不再卡死）应用到线上？**
它只改一个错误码。建议你先在线上用两个浏览器标签页编辑同一餐的老流程，看第二个保存是否卡住：卡住就说明线上也有这个问题，应该应用；不卡就可以不应用。**默认：不应用，等你验证。**

**Q3 怎么把迁移应用到线上？**
`20261023000100_coach_chat_foundation.sql`（新表、v2 函数、运动幂等）必须你明确同意才执行（charter H8）。我没有执行任何线上操作，只在本地仿真库验证过。**默认：你来执行，或授权我在分支库先跑。**

**Q4 开通哪几个账号？**
```sql
insert into public.user_features (user_id, feature_key) values ('<用户 id>', 'coach_chat');
```
同时需要在 Netlify 设置 `OPENAI_CHAT_MODEL`（以及已有的 `OPENAI_API_KEY`）。**默认：只开你自己。**

**Q5 `OPENAI_CHAT_MODEL` 选哪个？**
需要支持：Responses API + `json_schema` 严格模式。首次 `npm run coach:eval` 会暴露不兼容（尤其是我用到的嵌套 `anyOf`，见指南 §6-10）。**默认：先用现有 `OPENAI_MODEL`，评测后再换更快的。**

### 🟡 本周内

**Q6 对话原文要保留多久？**
现在是一直保留，直到用户清空或删号；日志里不存原话。另外**既有问题**：`ai_generations` 设计上保留 90 天，但自动删除任务一直没实现。**默认：保持现状。**

**Q7 餐别按时间推测的规则合不合你的习惯？**（早 4–10、午 10–14、加餐 14–17、晚 17–22、其余加餐；凌晨说晚饭会问昨天还是今天）**默认：按这个。**
