# PRD 01：食物照片识别

状态：草案 · 依赖：ADR-003/004/005、Q13 · 对应 Patch §3.2、§3.3、§7.1、§11.1（F01–F06、F30）、§11.2

## 1. 背景与目标
A 类用户熟悉训练后可能觉得记账没有新增价值；B 类用户会因为"要查食物、要称重"而逃避记录。拍一张照片、得到一张**可以改、可以不精确**的草稿，是降低记录门槛最直接的办法。
**目标**：把"记一餐"的主动操作降到 拍照 → 看一眼 → 确认；识别不准时能用一句话纠正，而不是重新填表。
**非目标**：热量精确度承诺（Patch §11.2：不承诺"准确率 XX%"）；身体进度照片分析（独立功能）；连续视频拍餐/强制参照物。

## 2. 用户与场景
| 场景 | 例 |
|---|---|
| 单张饭照 | 外卖/餐盘，默认意图＝记录这一餐 |
| 多张 | 同一餐多角度；或一次补记早中晚 |
| 照片＋一句话 | "这是昨天午饭，吃了一半" |
| 照片＋语音 | 同上，语音转写后可改 |
| 看不清/不是食物 | 要能优雅降级 |

## 3. 范围
**含**：拍照/选图（最多 5 张）、浏览器压缩与去 EXIF、私有存储、识别→草稿、份量范围与依据、不确定项展示、分组追问、纠正、删除图片、账号删除覆盖。
**不含（本期）**：空间体积估计（见 §10 试验支线）、条码/包装识别、菜单 OCR、相册批量导入。

## 4. 用户故事与验收
| ID | 故事 | 验收（对应测试） |
|---|---|---|
| P1 | 我拍一张饭，得到草稿，不会自动保存 | F01：草稿 `proposed`；库里无记录；确认后仅一条规范记录 |
| P2 | 我说"这是昨天中午的" | 日期由服务端解析；F21 |
| P3 | 照片里有我没吃的东西 | 可以一句话"不吃汤" → 编辑草稿；F15/F17 |
| P4 | 看不清时系统别乱猜 | F05：明确不确定，可文字或粗记；**最多提示一次重拍** |
| P5 | 三张图不要默认三餐 | F03：一次澄清；未答则保留未归属草稿（F31） |
| P6 | 同一道菜拍了两个角度不要加倍 | F04：视角合并，份量不相加 |
| P7 | 我能删掉我的照片 | 删除后对象+元数据都没了；已保存的文字记录不受影响 |
| P8 | 混合菜不要假装能拆 | F06：整菜 provisional 估算，或仅列出可见食材，不编造油量/配方 |

## 6. 功能需求
| ID | 需求 | 说明 |
|---|---|---|
| R1 | 格式/大小 | JPEG/PNG/WebP；单次≤5 张、单张≤10MB（Patch 初始值，**需部署验证**）；服务端校验魔数与实际大小，不信任客户端 |
| R2 | 预处理 | 浏览器压缩（长边约 1280–1600px，数值待实测）；canvas 重编码去 EXIF；EXIF 拍摄时间仅作参考，不保存、不当进餐事实（Patch §5） |
| R3 | 存储 | 私有桶 + 限时签名读取；无永久公开 URL；对象键含 user_id；见 ADR-003 |
| R4 | 识别输出契约 | `candidates[]：{name, dish_kind(single/mixed/drink/packaged), visible_basis, portion:{low, mid, high, unit}, confidence_note?}` + `unknowns[]`（看不见的油/隐藏食材/不确定的汤）+ `quality: ok|blurry|dark|not_food|mixed_views`。**不输出百分比置信度**，不输出营养 |
| R5 | 营养 | 复用 `resolveItems`：个人记忆 > 标准库精确命中 > 估算；份量优先级：用户明确 > 已确认的个人份量/容器 > 份量模板 > 视觉估计（Patch §7.1）；营养永远由服务端算 |
| R6 | 草稿 | 走现有 `meal` 草稿（`payload.media_ids`、`source:'photo'`）；卡片展示依据与不确定项；**用户确认＝接受本次记录，不升级为测量真值或标准库**（沿用 D-10） |
| R7 | 追问 | 多图分组是**唯一**默认追问；其余不确定一律估算并标注。每个记录任务总预算仍是 1 次 |
| R8 | 降级 | 任何失败都能退到文字或"只记吃了什么"；不无限要求重拍 |
| R9 | 保留与删除 | 默认保留期见 ADR-003（建议 7 天，待你定）；用户可随时删；账号删除覆盖对象+元数据+聊天关联；图片失效不影响已有文字/营养记录可读性 |
| R10 | 防注入 | 图片内文字/菜名里的"指令"只当数据；识别结果不得触发任何写入；视觉输出同样走 schema 校验 |
| R11 | 观测 | 记录阶段耗时（压缩/上传/识别/草稿）、模型版本、token；**不记录图片内容/用户原话** |

## 7. 非功能
- **延迟**：以真实部署实测 p50/p95 为准；超过上限必须拆请求/限时降级，**不允许无限等待**（Patch §11.2）。没有数据前不写"性能通过"。
- **成本**：每张图的 token 随尺寸变化；上限（张数×尺寸）本身就是成本控制。每用户每日上传上限（建议起步 20 张，待定）。
- **无障碍**：图片附件有文字替代（"食物照片 1"）；识别阶段用 `aria-live`。
- **离线**：上传失败时保留本地预览并可重试；**不得**在未确认时本地保存草稿为"已记录"。

## 8. 质量评估（Patch §11.2，分开测）
1. **确定性部分**（每 100g/份数换算/求和/四舍五入/修改重算）：固定夹具，精确一致。**不能用视觉误差掩盖程序算错。**
2. **视觉部分**：≥30 个有真实标签的餐食（称重/包装/制作记录；**不用另一个 LLM 当真值**）：
   | 类别 | 最少 |
   |---|---|
   | 中式家常/外卖混合餐 | 10 |
   | 清晰可分食材餐 | 5 |
   | 饮品/包装/汤类 | 5 |
   | 同餐多图/遮挡/低光 | 5 |
   | 份量相近但容器不同 | 5 |
   （可交叉，需报告覆盖；优先用户常吃食物。）
3. **报告项**：食物遗漏与误认、可称重子集的重量 MAE/相对误差、低质图拒识/降级、缺失营养率、用户纠正次数、总耗时及分项、模型版本/成本。
4. **发布门槛**（Patch 默认，可调）：F01–F32 与全部写入/权限/日期/计算测试通过；30 例中 ≥27 例在"至多一次澄清＋正常确认/纠正"下完成正确事实记录或如实待补（**全部降级成粗记不算通过**）；任何 ≥2 倍重量误估且无不确定性/修正路径 = 阻断；任何静默丢单/重复记账/越权/虚假保存 = 阻断。
5. **需要你提供**：30 例标注样本（或授权我设计采集方案）。没有它，视觉质量就**只能写"未评估"**。

## 9. 隐私与合规（上线前必须一致）

- 默认不用于训练；不承诺做不到的删除时效（例如供应商侧日志保留）。
- 同步更新：`app/privacy/page.tsx`、`docs/legal/LEGAL_BRIEF.md`、`lib/site/features.ts`（`food-photo` 已是"规划中"，**内测可用前不得改"内测中"**）。

## 10. 试验支线：空间估算（不阻塞主线）
- 接口：`estimatePortion({photo, optionalScale, optionalUserInfo}) → {estimated_weight, range, method, basis, unknowns}`；可切换"视觉+模板"或"几何增强"。
- 研究参考（**均未复现**，许可需逐项复核）：food_volume_estimation（MIT，旧 TF 依赖，先离线）、Depth-Anything-V2（仅 Small 权重 Apache-2.0；相对深度≠物理毫升）、FoodSeg103（分割基准）、VolTex（GPL-3.0，仅研究参考）、Nutrition5k（评测补充）。
- 约束：只在**隔离服务/离线实验**里跑，不塞进 Netlify 函数；体积→重量仍依赖密度与尺度标定；几何不能识别不可见油量；**只有对照数据证明收益且部署/许可清楚才接主流程**。

## 11. 风险
| 风险 | 缓解 |
|---|---|
| 视觉模型份量误差大 | 范围+依据展示、"估算"标注、一句话纠正；门槛里的 2 倍误估阻断 |
| 隐私承诺与实际不符 | 上线闸门：隐私文案核对清单（`10`） |
| 函数超时（A4） | 直传 + 识别独立请求 + 限时降级 |
| 真机格式差异（HEIC/WebP） | iOS/Android 真机矩阵（A5） |
| 图片内注入 | R10 + F32 图片用例 |
| 保留期清理没落地 | ADR-010；清理任务上线前不开放照片 |
