# 架构决策记录（ADR）

格式：背景 → 选项 → **建议** → 后果 → 可逆性。状态都是"提议"，评审后改为"采纳/否决"。
ADR-001、002 已在 PR #18 中实现，这里只记录以便后续 ADR 引用。

---

## ADR-001 计划-执行，而不是原生工具调用（已实现）
- **背景**：聊天要调用多个业务能力（记饮食、记运动、查当天……）。
- **选项**：A 原生工具调用循环；B 模型一次输出结构化计划，服务端执行。
- **决定**：B。理由：写入可靠（模型不接触工具）、调用次数固定（要最快的模型）、数字不由模型产生。
- **后果**：模型"读错"只会产生一张可见的卡片；开放式多步推理能力受限。
- **可逆性**：高。工具定义可直接映射成 tools。详见 `../XIAOZHUA_PROMPT_GUIDE.md` §1、§7。

## ADR-002 草稿—确认是唯一写入路径（已实现）
- **决定**：聊天只生成 `coach_drafts`；确认接口只提交服务端保存的内容；内容不可变，改动 = 新草稿 + 新 request_id。
- **新功能必须遵守**：照片识别结果、语音转写后的记录、食谱"按这份吃了"，**都走同一条路径**，不得另开写入口。

## ADR-003 食物照片存放：私有桶 + 签名直传 + 限时读取
- **背景**：照片含家庭环境、可能含人脸/餐具之外的信息；隐私页现在写"不收集照片"，必须改且要兑现。
- **选项**
  - A. 经过 Next/Netlify 函数中转上传（浏览器 → 函数 → Storage）。
  - B. 浏览器用**签名上传 URL**直传 Storage；函数只发 URL 和接收"完成"通知。
  - C. 不存图，识别完立刻丢弃，只存识别结果。
- **建议**：**B 为主，保留 C 作为用户可选的"识别后即删"**。
  - 直传绕开函数的请求体大小/超时限制（A4，Netlify 数值未知）。
  - 私有桶，对象键 `food/{user_id}/{media_id}.jpg`；RLS 只允许本人读写本人前缀；**不生成永久公开 URL**，读取一律限时签名 URL。
  - 默认保留期：识别草稿确认或取消后 **7 天删除原图**（保留文字记录）；用户可随时手动删；账号删除时一并删（对象 + 元数据）。
  - C 作为设置项"识别后不保留照片"，对隐私敏感用户更友好，代价是无法在对话里回看图片、无法复盘识别错误。
- **后果**：要建桶与策略（线上基础设施，我不能代做）；要一个"过期清理"任务（目前仓库没有任何定时任务，见 ADR-010）；隐私页必须改并披露 OpenAI 会处理图片。
- **可逆性**：中。桶和策略一旦有用户数据就不好改结构，所以先定对象键规范。
- **待你决定**：保留期（7 天？30 天？）、默认保留还是默认不保留（Q13）。

## ADR-004 图片预处理放在哪里
- **选项**：A 浏览器里压缩+去 EXIF（canvas 重编码）；B 服务端处理（需要 sharp 等原生依赖，Netlify 上是否可用未知）。
- **建议**：**A**。canvas 重编码天然丢弃 EXIF；长边限制 1280–1600 px、JPEG 质量约 0.8（数值待实测调优）；HEIC 由系统/浏览器转换（A5）。服务端只做**魔数校验和尺寸上限校验**（不解码大图）。
- **后果**：压缩行为随浏览器而异，需要真机矩阵测试；服务端不能信任客户端声明的类型，必须校验魔数。
- **EXIF 拍摄时间**：压缩前读取 `DateTimeOriginal` 仅作为**参考**（Patch §5：不能当进餐事实），不随图保存。

## ADR-005 视觉识别：独立请求，不塞进聊天回合
- **背景**：图片识别耗时明显长于文字计划；放进同一个聊天请求会撞超时（A4）。
- **选项**：A 同一请求里先识别再计划；B 拆成"上传完成 → 识别（独立请求）→ 草稿"，前端用阶段状态展示。
- **建议**：**B**。聊天回合只接收 `media_ids`，识别结果作为"已解析的食物候选"进入既有的 `resolveItems`（匹配/份量/估算/草稿全部复用）。
- **接口形态**：`POST /api/coach/media/[id]/analyze` 返回候选列表（同步，带超时上限）；超时则返回 `retryable`，不无限等待。
- **约束**：识别只输出 **食物候选 + 份量范围 + 可见依据 + 不确定项**；油量/隐藏食材不得写成已知（Patch §7.1）。识别结果是**估计输入**，营养仍由服务端算。
- **模型适配**：用 `lib/coach-chat/vision.ts` 作为 adapter，先验证实际模型能力（A1）再选定供应商，不隐式切换（Patch §2）。

## ADR-006 语音：产品内录音 + 服务端转写，不长期保存音频
- **选项**：A 系统键盘听写（零开发，Patch 说只能作过渡）；B 浏览器 Web Speech API（iOS PWA 不稳）；C `MediaRecorder` 录音 → 上传 → 服务端转写 → 文字回填输入框。
- **建议**：**C**；A 作为兜底提示。
- **关键约束**：转写后**回填可编辑文字，用户点发送才进入聊天回合**（转写错误不得自动落账）；单段上限 60 秒（可配）；音频处理后立即删除（默认不保存，Patch §7.2），隐私页如实披露。
- **后果**：要真机验证 iOS/Android 编码格式差异（A6）；需要麦克风权限的失败兜底（拒权、无声、超时、上传失败各有明确文案）。

## ADR-007 食谱来源：白名单 + 管理员触发的小批导入 + 只存元信息与外链
- **背景**：Patch §8：指定 UP 主；不要求用户逐条维护；不能绕过登录限制；不能虚构。
- **选项**：A 实时抓取（用户点开时才抓）；B 后台批量爬取整个主页；C 白名单来源 + 管理员给少量链接 → 导入器取元信息 → 人工核对后上架。
- **建议**：**C**。
  - 只存：标题、来源、原链接、可选封面链接/用时/食材、获取时间、获取状态；**不转存封面图片**（版权与存储），封面用外链或占位图兜底。
  - 字幕/视频内容**v1 不取**（A7：不稳定，且合规风险高）。
  - 作者标注的热量只作"作者标注"显示，份量口径不清则隐藏；**永不进入摄入事实**。
- **后果**：内容量小但可控；需要导入器的 og 元信息解析与去重；失败的链接保留为"仅标题+链接"卡。
- **待你决定**：来源链接（Q15）、条款是否允许（我无法替你判断）、是否允许外链封面。

## ADR-008 偏好模型：三层 + 只在用户明确表达时写入
- **选项**：A 单表单字段；B 三层（硬限制 / 软偏好 / 本次条件）分存；C 让模型自由总结"用户画像"。
- **建议**：**B**，**禁止 C**。
  - 硬限制（过敏、长期不吃）：用户明确说才写入，**可即时生效并告知**，可查/改/删；配料不全不能保证适配过敏限制。
  - 软偏好（口味、做饭条件）：来自显式表达或点赞/点踩的**有依据**推断；一次点踩不变成永久禁令。
  - 本次条件（"明天不吃鱼"、"只有15分钟"）：只作用于本次推荐，**不落长期记忆**。
  - 病史**不默默写入**长期记忆；需要知情选择（Patch §9）。
- **后果**：模型不能直接写偏好，偏好变更同样走"提议—确认"（硬限制可例外：即时生效 + 明确告知 + 一键撤销）。

## ADR-009 提示频控放服务端表，不放 localStorage
- **理由**：Patch/旧 Spec 要求"每天最多一个、关闭状态跨会话"。localStorage 换设备/清缓存就失效，且无法统计。
- **建议**：`coach_nudges` 表（见 `09`），"今天是否已展示"由服务端按用户时区的当地日期判定；客户端只负责渲染与上报关闭。
- **内容**：固定模板，不调用模型（旧 Spec A7）。

## ADR-010 异步与定时：先不引入队列，按需选最小方案
- **背景**：照片过期清理、气泡生成、食谱导入都需要"不在用户请求里"的工作；仓库目前**没有任何定时/后台任务**。`ai_generations` 设计的 90 天清理也一直没实现。
- **选项**：A Supabase `pg_cron`（若项目启用）做纯 SQL 清理；B Netlify 计划函数（Scheduled Functions，是否可用待核实）；C 惰性清理（用户下次访问时顺带清）；D 外部 cron 调用受保护的接口。
- **建议**：**A 优先（纯 SQL 的清理）**，C 作兜底；导入器用管理员手动触发（D 的人工版）。不为此引入队列服务。
- **待核实**：Supabase 项目是否启用 `pg_cron`；Netlify 计划函数可用性。
- **顺带收益**：同一机制可以兑现 `ai_generations` 的 90 天保留，这是目前隐私文案里"待核实"的一块。
