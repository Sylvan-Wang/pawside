# 照片上传、聊天输入框、相册与每日复盘配图（需求草案）

来源：产品负责人口述（2026-10-23）。关联：`01-PRD-food-photo.md`（识别）、`11-requirements-daily-loop.md`（日终总结）。

## 现状（对照代码）

- **应用里没有任何照片上传入口**：全仓库没有 `type="file"`、没有 `capture`、没有 Storage 桶。网页版和手机端都一样。
- 小爪聊天面板的输入框只有文字。
- 所以"从微信拖一张图到网页"和"手机上传"目前都做不到。

## 需求整理

### A. 聊天输入框（参考微信）
1. 输入区：文字框 + 「+」（或回形针）按钮 + 发送。
2. 「+」展开：拍照、从相册选择；桌面浏览器额外支持**拖放**和**粘贴**（从微信/文件夹拖一张图进聊天框）。
3. 选图后先在输入框上方显示缩略图（可删除、最多 5 张），再发送；不选就不上传。
4. 手机端要真机验证：iOS Safari、Android Chrome、微信内置浏览器（相册和相机权限表现各不相同）。
5. 键盘弹起时输入区不被遮挡（沿用现有 visualViewport 处理）。

### B. 照片的去向
1. 聊天里发的饮食照片：用于识别成饮食草稿（见 01），保存饮食记录时，用户可选择"把这张照片附在这一餐上"。
2. 不是每张发给小爪的图都要进相册：默认只在**用户确认保存的那一餐**上留图；没确认的草稿图随草稿过期删除。

### C. 相册（设置里）
1. 设置里新增「相册」：按日期展示用户留存的照片，点开看大图和当天记录。
2. 支持删除单张、批量删除。删照片不影响已保存的文字记录。
3. 照片来源：饮食照（本期）；以后可加训练/身体变化照（需要另做隐私评估，不在本期）。

### D. 每日复盘配图
1. 每日复盘 = 训练情况 + 饮食情况 + 总体评价。
2. 「饮食情况」部分附当天各餐的照片缩略图，方便回忆。
3. 复盘文字仍由服务端按记录算数、模型只写不含数字的点评；**照片是否交给模型，默认否**（识别时才用，复盘不再喂图）。

## 关键约束与建议

- **照片是敏感数据**：必须私有存储（Supabase Storage 私有桶 + 行级权限，只有本人能读），用短时签名链接展示，不用公开 URL。
- **隐私文案必须先改**：隐私页现在写的是"不收集照片"，上线前要如实改成收集、给谁（识别时发给模型服务商）、保留多久、怎么删。账号删除与导出必须覆盖照片。
- **上传前在浏览器压缩并去除 EXIF**（定位等信息），限制大小和格式；HEIC 要么转换要么明确不支持。
- **每个文件校验类型与大小**，服务端不信任浏览器给的类型。
- **存储成本与上限**：每人总量上限、单餐最多 5 张、过期草稿图定时清理（需要清理任务，目前仓库没有定时任务机制）。
- 上传失败/断网要可重试，且不重复占用存储（幂等的上传 id）。
- 相册只是已保存记录的"视图"，不单独成为写入来源。

## 待决问题

1. Supabase Storage 私有桶需要你在线上创建并授权（我无法替你做）。
2. 照片保留多久：永久（直到用户删）还是有期限？建议用户可控，默认保留。
3. 微信内置浏览器是否是主要使用场景？它对相机/文件选择有限制，要真机测。
4. 是否本期就做识别（拍照→草稿），还是先做"上传+相册+复盘配图"、识别稍后。我建议先上传存档，再接识别，风险分开。
5. 每日复盘本身（见 11）还没做，配图依赖它。

## 建议分期

1. 上传基础：聊天输入框改造（+、缩略图、拖放、粘贴）、私有桶、压缩去 EXIF、隐私文案。
2. 饮食照附到保存的餐；设置里相册。
3. 每日复盘配图（依赖日终总结）。
4. 照片识别成草稿（01）。
