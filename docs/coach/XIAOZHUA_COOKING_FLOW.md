# 小爪「今天做什么菜」全流程方案（草案，2026-11-21）

来源：xxa 11-21 在项目线程里描述的流程。本文把它对到现有代码，说明哪些已经有、要新做什么、按什么顺序做，以及需要 xxa 拍板的地方。**这是方案，不是已实现的功能**，官网不写。

## 0. xxa 描述的流程

> 我跟小爪说「我今天想做个减脂餐，但不知道吃什么」。
> 1. 小爪问：中餐还是西餐？→ 我选中餐。
> 2. 小爪问：有没有过敏或不吃的？列出海鲜、菌菇……和「其他」。→ 我选了，比如「其他：香菇」。
>    - 这些要**存进我的档案**，下次不用再问；
>    - 还要**反过来筛菜库**：入库时就把每道菜的配料拆出来，判断是不是以香菇为核心原料，是就不推给我。
> 3. 小爪给 A、B、C 三道菜。→ 我说要 C。
> 4. 小爪给 C 的具体原材料（买什么、多少）、要准备的调味品，最下面是做饭视频，点了跳到 UP 主那里。
>
> 菜库要持续更新，中餐西餐都要有，可以从 NYT 这类海外网站补充。

## 2. 要新做的

### 2.1 多轮的「点菜」对话（不新增 AI 用途）

整个流程**由程序走，不由模型走**。模型只负责一件事，和现在一样：认出用户是在「要推荐菜」。之后每一步的问题、选项、菜名、数字都由代码生成，用户点按钮或打字回答。

```
要推荐 ──► [档案里还没有忌口？] ──是──► 问忌口（多选 + 其他）──► 存档案
   │                                                        │
   └──────────────否───────────────────────────────────────┘
                              ▼
                     问：中餐 / 西餐 / 都行
                              ▼
                 按忌口筛菜库 → 按今天剩余目标排序 → 给 A B C
                              ▼
               用户选一道 → 食材清单（买什么、多少）+ 调味品 + 视频
```

- 状态存在对话里（和现在的待确认草稿一样，放在 `coach_drafts` 或对话的 metadata 里），用户中途说别的话，流程就自然结束，不追着问。
- 已经存过忌口的人跳过第 2 步。用户说「我现在不吃牛肉了」，就更新档案。
- 顺序和 xxa 描述的稍有不同：**忌口先问，只问一次**，以后每次直接问中餐还是西餐。原因是忌口一旦存进档案就很少变；每次都问，会多出一步。

### 2.2 档案里的忌口（要改数据库结构）

新增一张表 `user_food_restrictions`（或在 profile 上加一个 jsonb 列）。每一条记两件事：

- **什么**：大类（海鲜、贝类、菌菇、花生、坚果、蛋、奶、大豆、麸质、牛肉、猪肉、香菜……）或「其他」里写的具体食材（香菇）。
- **严重程度**：`allergy`（过敏）或 `dislike`（不吃 / 不喜欢）。**这两种必须分开。** 原因见 2.3。

用户在设置里能看、能改、能删。导出数据、删除账号时，这张表一起处理。

### 2.3 菜库：每道菜拆出配料，并且分「主料 / 配料 / 调味」

现在每道菜的 `ingredients` 已经拆到食物库 `food_id`。还缺三样：

1. **角色**：每样食材标 `core`（主料，比如香菇滑鸡里的香菇）、`side`（配菜）、`seasoning`（调味品）。
2. **调味品单独列出来**：现在生抽、蚝油、豆瓣酱这些只写在做法那句话里，没有结构化。要拆成清单，因为它们既是「要准备的调味品」，也是过敏原的主要来源（蚝油里有贝类，生抽里有大豆和小麦）。
3. **食材 → 过敏原大类** 的对照表，比如 香菇→菌菇、虾仁→海鲜/甲壳类、炒花生米→花生、生抽→大豆/麸质。

筛选规则：

| 用户档案 | 排除哪些菜 |
|---|---|
| 不吃（dislike） | 这样东西是**主料**的菜（xxa 说的「以香菇为核心原料」）。它只是配料的，照样推荐，并在菜下面写一句「配料里有香菇，可以不放」 |
| 过敏（allergy） | **任何**一样食材或调味品里有它的菜，都不推荐。过敏不能按「是不是主料」来判断：宫保鸡丁里只放 10 g 花生，对花生过敏的人照样危险 |

过敏筛选是安全相关的规则，要有单独的测试，并在回复里写一句「请再看一眼配料，加工食品的成分以包装为准」。我们不能保证调味品的品牌成分。

### 2.4 选好一道菜之后给什么

- **原材料**（一人份，可以按人数乘）：名字、克数、生熟口径，按买菜的分类排（肉蛋、蔬菜、主食）。数字已经有了，就是菜库里的克数。
- **调味品**：2.3 拆出来的调味清单，标出「家里常备」和「可能要买」。
- **热量和蛋白质**：和现在一样，由代码按食物库算，标明是估算。
- **做饭视频**：只有这道菜在 `recipes` 表里有**已核验、已发布**的视频对应时才显示，点了跳到 B 站（西餐可以是 YouTube）。没有就不显示，不拿别的菜的视频凑数。这需要在菜和视频之间建对应关系（`recipes.meal_idea_code`），每一条由人核对过后再发布。

### 2.5 西餐和菜库扩充

现在 146 道全是中餐，「西餐」这一支要先补菜。关于从 NYT 补充：

- **不建议抓取 NYT Cooking。** 它的使用条款禁止自动抓取，也禁止转载菜谱正文和图片；它是付费内容。
- 建议做法：
  1. 我们自己写西餐家常菜，格式和现有 146 道一样（食材对到食物库、克数、一句话做法、调味清单），营养由我们算，可以核对。菜名和常见搭配这类常识可以参考公开资料，但不复制任何网站的正文。
  2. 视频只存链接（B 站 / YouTube 的 UP 主），和现在 `recipes` 表的规则一样：不存视频、不存封面、不抄做法文字。
  3. 例程每周补 10 道（中西各半），每道都要过 `tests/coach-chat/meal-ideas.test.ts` 的数值核对。

## 4. 「从零开始」的全流程测试

xxa 要求小爪能覆盖各种情况，尤其是想控制饮食的人从「不知道吃什么」到做好一道菜的全过程。测试分两层：

**程序层（vitest，不调模型，每次 CI 都跑）**：
- 每一步给出的选项和下一步对得上；中途换话题，流程结束，不留残留状态。
- 忌口：dislike 只排除主料、allergy 排除任何成分、「其他：香菇」也能生效、档案里的忌口下次自动带上。
- 没有符合条件的菜时（比如过敏项太多），说清楚「菜库里暂时没有合适的」，不推一道不合适的。
- 数字都能从食物库复算。

**模型层（`npm run coach:eval`，真实模型）**：补一组用户原话，确认都能进入点菜流程，且不会被当成记录：
- 「今天想做个减脂餐，不知道吃啥」「想吃点辣的，减脂期能吃什么」「晚上自己做饭，买什么菜」「冰箱里有鸡胸和西兰花，能做什么」「想吃西餐，简单点的」「不吃香菇，推荐个菜」「我对虾过敏」「这道菜要买什么调料」「第三个」「换一批」
- 还有反例：「我中午吃了宫保鸡丁」应该是记录，不是推荐。
